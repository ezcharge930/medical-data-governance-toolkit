# 领域认知缺口（思维层面）

- **数据治理不等于把生成标准格式数据**
- **数据治理 = 控制 + 透明 + 责任**
- **缺少关键认知**

| 我认为的治理           | 实际医疗数据治理要求                      |
| ---------------------- | ----------------------------------------- |
| 输出符合 CDSIC 的 csv 文件 | 输出 + 血缘图谱 + 质量报告 + 敏感字段清单 |
| 配置写全了就安全       | 配置本身需版本控制、审批、变更审计        |
| 数据来自医保所以安全   | 必须主动验证并记录数据敏感级别            |

- **提升建议**
  - 精读《医疗卫生机构数据安全管理办法》《个人信息保护法》第 73 条（匿名化定义）
  - 研究 FDA 对临床数据提交的审计要求（如 21 CFR Part 11）
  - 学习 DAMA-DMBOK 中“数据治理”“数据质量”“元数据管理”章节
  - 元数据管理相关笔记，请参阅 [元数据管理](./元数据管理.md)
  - 数据质量相关笔记，请参阅 [数据质量](数据质量.md)

# 架构设计缺口（工程思维层面）

- **治理型架构的核心特征**
  - **可观测性**：每一步操作可记录、可查询  
  - **不可变性**：输出结果附带输入快照（如配置哈希）  
  - **策略驱动**：脱敏规则、质量规则、访问规则外置为策略，而非硬编码  

| 场景     | 我目前当前做法  | 治理性做法                                                 |
| -------- | --------------- | ---------------------------------------------------------- |
| 字段处理 | 直接清洗输出    | 先识别敏感级别 &rarr; 应用脱敏策略 &rarr; 记录处理日志      |
| 任务执行 | 打印 "处理完成" | 生成任务元数据（谁、何时、用何配置、输入/输出结果）        |
| 错误处理 | 返回空 DataFrame | 抛出结构化异常（含数据集、字段、错误类型），供监控系统捕获 |

- **提升建议**
  - 学习 `Policy Pattern`（策略模式）：将合规规则抽象为可插拔策略  
  - 研究 `OpenLineage`、`Marquez` 等开源血缘框架的设计  
  - 在现有代码中尝试添加 `AuditLogger` 模块，记录关键操作

# 工程实践缺口（执行层面）

- **医疗数据工具的工程底线**
  - 必须有测试：核心逻辑 100% 覆盖  
  - 必须可复现：任务输出 = f(输入数据 + 配置 + 代码版本)  
  - 必须可隔离：多项目并发无干扰  

- **目前缺失的实践**
  - 单元测试  
  - 配置校验  
  - 工作空间隔离  
  - 安全输入处理  

- **提升建议**
  - 为 `DM` 类补全 `pytest` 测试（从 `_map_sex` 开始）  
  - 在 `ConfigurationService` 中增加配置 `schema` 校验  
  - 引入 `click` 或 `typer` 替代 `argparse`，支持工作空间参数
